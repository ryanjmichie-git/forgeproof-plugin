## Resolved questions (decided with Ryan, 2026-08-11)

| Question | Decision |
|---|---|
| How to sign the DSSE envelope stdlib-only (SSHSIG is not a raw signature cosign can read) | **Same key, seed parsed from the OpenSSH private key.** Pure-Python RFC 8032 Ed25519; the 32-byte seed comes out of the unencrypted `openssh-key-v1` file `generate_ephemeral_keypair` already writes. ONE identity signs the SSHSIG chain/bundle signature *and* the DSSE. The parse asserts the derived public key equals the `ssh-ed25519` blob, so a parse bug dies loudly instead of signing with the wrong key. |
| Where the attestation lives | **Embedded in the `.rpack` under a new top-level `attestation` key**, plus a byte-identical sidecar export (`issue-N.sigstore.json`) and the key as `issue-N.pub.pem`. `cmd_verify`'s root-digest *denylist* (`forgeproof.py:1194`) covers the embedded copy for free and lets old verifiers pass new bundles. |
| Human approval events (the engine records none today) | **New `approval` chain action**, recorded by the run skill at the Phase-1 plan gate. The engine fills `approver` from `git config user.email` rather than trusting a flag. The predicate labels these `evidence: agent-recorded` — the AI asserts the human approved; it is not cryptographic proof of consent (Principle 3). |
| Verify posture on a broken attestation | **Red — tamper class**, for everything inside the signed bundle. Absent attestation ⇒ check `skipped`, zero errors and zero warnings in **every** mode including `--strict`. |
| Sidecar byte-equality at verify time | **Dropped.** `cmd_verify` performs **zero filesystem reads for attestation purposes** — it never stats, reads or compares the sidecars in any mode. Byte-identity is an **emission** invariant (pytest + stress), not a verification one. Rationale in finding 6. |
| `cosign-interop` CI gate | **Required, with the cosign *binary* version pinned** (not just the installer action SHA), so upstream cannot break the build without a deliberate pin-bump PR. |
| Compliance-doc framing | **Lead with the current state:** SSDF is a voluntary reference standard, not a procurement mandate (finding 7). Map to the CISA form's item 3 and its SSDF task IDs as the durable technical target; frame the CRA strictly as "may serve as an element of the Annex VII technical file, at the manufacturer's discretion". |
| `finalize` when the key cannot be parsed | **Hard fail with a clear message, before the chain is mutated.** An attestation in every v1.3 bundle is the product promise; degrading silently would produce two tiers of output that no test could tell apart. |

## Context

v1.2.2 shipped 2026-07-18 (`b8db908`, tagged; the community marketplace pin has caught up). ROADMAP v1.3.0 is **"Speak the industry's language"** (ROADMAP.md:76-86): a `.rpack` today proves integrity only to ForgeProof's own verifier, while supply-chain security has standardized how attestations are expressed (in-toto, SLSA, DSSE). This release makes every bundle *also* a standards-conformant attestation. Success criteria: **the emitted attestation verifies via cosign with no ForgeProof code present**, and the `.rpack` stays backward-verifiable.

### Research findings that shape this plan (verified 2026-08-11 against the live code and primary sources)

1. **Additive top-level bundle keys are safe in both directions — by accident of an existing implementation choice.** `cmd_verify` recomputes the root digest with a *denylist*: `{k: v for k, v in bundle.items() if k not in ("root_digest", "signature")}` (`forgeproof.py:1194`). So `attestation` is inside `root_digest` with zero code change, **and the v1.2.2 verifier vendored in `forgeproof-verify@v1.0.2` verifies v1.3 bundles green** because it hashes keys it has never heard of. This one line is what makes the whole design cheap; excluding `attestation` there would make it swappable on a green bundle. A source-grep test must pin it.
2. **A new chain action is invisible to old verifiers.** `cmd_verify` checks per-block hash and `prev_hash` linkage only (`:1277-1297`); it never enumerates action names, and `cmd_finalize`'s collector loop (`:860-878`) ignores unknown ones.
3. **cosign v3 deprecated the bare-envelope path.** `--signature` is registered but hidden and deprecated (`"please use --bundle to provide a signature"`); v3.0.0 defaulted to the protobuf bundle. So the **Sigstore bundle is the emission target**, not a bare DSSE envelope — which is also the v1.4-shaped hole: `verificationMaterial` is exactly where a Fulcio cert and Rekor `tlogEntries` go, with the envelope inside untouched.
4. **Ed25519 vs Ed25519ph: plain Ed25519 wins, and the folklore is wrong.** sigstore/sigstore PR #1595's *release note* claims `LoadSigner`/`LoadVerifier` default to the ph variant; the merged diff does the opposite — `var useED25519ph bool` defaults `false` and is only flipped by `options.WithED25519ph()`, which cosign never passes (`LoadDefaultVerifier`/`LoadVerifier` both call through with zero opts). A stale doc comment in `algorithm_registry.go` repeats the false claim. Confidence high, not certain — Phase 0 settles it empirically by signing both ways.
5. **cosign cannot produce Ed25519 signatures at all.** `--signing-algorithm` in v3.1.3 allows only ECDSA and RSA variants, so cosign's Ed25519 `--key` *verify* path has no upstream round-trip coverage. Treat interop as empirically validated against a pinned binary, never as a load-bearing contract; ForgeProof's own verifier stays the source of truth.
6. **A sidecar check at verify time is all cost and no detection.** Checks over `bundle["attestation"]` are inside `root_digest`; the sidecar is the one thing verify would read that no signature covers. `prettier --write .`, a pre-commit JSON formatter, or an editor adding a BOM would print TAMPER DETECTED on a cryptographically perfect bundle — and "missing sidecar" as a strict error would turn the Action (strict by default) red on any bundle copied out of a PR. Tampering the sidecar breaks its own DSSE signature, which cosign catches. Hence the dropped check.
7. **The US federal frame in the ROADMAP is out of date.** OMB **M-22-18 and M-23-16 were rescinded 2026-01-23** by **M-26-05**, which calls them "unproven and burdensome" and says agencies *may* use the CISA Secure Software Development Attestation Form as an optional resource; CISA's form page now carries an "Archived Content" banner. The durable target is the form's **item 3 — "maintains provenance for internal code and third-party components"** → SSDF `PO.1.3, PO.3.2, PO.5.1, PO.5.2, PS.3.1, PS.3.2, PW.4.1, PW.4.4, RV.1.1, RV.1.2`. Also verified: **no SSDF practice or task addresses AI authorship of code** — a clean, citable gap.
8. **`chain_hash` is not the file's byte digest.** It is `sha256_hex(chain_path(issue).read_text())` (`:966`) — LF-normalized decoded text — while `save_chain` writes with default newline translation, so the file on disk is CRLF on Windows. Any predicate field described as "sha256 of the chain file" is wrong on every Windows-authored bundle, and a byproduct recomputed with `sha256_file` would make verify false-red on 100% of Windows runs while passing on Linux.
9. **`Path.write_text` translates `\n` to `\r\n` on Windows.** The sidecar is therefore canonical JSON with **no newline characters at all**, written with an explicit encoding and `newline=""` — nothing for Python or git to translate. Never copy `save_chain:253` or the rpack write at `:980`, both of which append `"\n"` with default translation.
10. **`_RECORD_DATA_FLAGS` is a silent-drop trap.** A flag declared in `build_parser` but missing from that list (`:643-648`) is invisible to the missing/unexpected guard — the value is dropped and cross-action misuse is accepted. `_record_data_from_flags` also ends in an *unguarded* lint-result return (`:739`), so adding `approval` to `RECORD_FLAG_SPEC` without a branch seals a lint-result-shaped dict built from unset attributes. Same class as the `read_json_file`/`gate-pr`/`lint-hook` miss.
11. **`TAMPER_ERROR_MARKERS` matches by substring** (`:1048-1049`) and already contains `"hash mismatch"` and `"prev_hash"`. A new error string containing either fragment becomes tamper-class by accident; one whose marker is never registered renders as VERIFICATION FAILED instead of TAMPER.
12. **Nine in-test bundle builders stamp `fp.RPACK_VERSION`** (`test_forgeproof.py:94, 662, 842, 882, 1456, 1473, 2241, 2314, 2562`) and cannot carry an attestation. Any "version ≥ 1.1.0 implies attestation" rule would turn the frozen legacy-JSON snapshots red — so `KNOWN_RPACK_VERSIONS` is a **membership set only, never an ordering**, and there is no version→attestation implication anywhere.
13. **The Action's `UPSTREAM` chicken-and-egg is solved, with a caveat.** v1.2.0 pinned it to the pushed release-branch commit SHA, then re-pinned to the tag (`PLAN_v1.2.0.md:106`). That only holds if the release PR is merged with a **merge commit** — squashing orphans the SHA and the sync-check goes permanently red.
14. **The release PR is not gated.** `verify-provenance.yml:23` runs only on `forgeproof/*` head branches, so nothing exercises the new Action against a new-format bundle before the tag. v1.2.0 covered this with a throwaway draft PR; v1.3.0 needs a three-case matrix.
15. **PRIVACY.md is already inaccurate, before the approver email.** Both frozen fixtures carry `public_key = "ssh-ed25519 AAAA… User@PC-951318"` — `ssh-keygen`'s default comment embeds `username@hostname`, and `read_public_key` stores the whole line. The "no personal information beyond the GitHub issue" claim needs correcting, not just extending.
16. **README numbers drift and CI cannot catch it.** README claims 168 tests (the suite collects 198), says "two frozen fixture bundles" (this release makes three), and promises compatibility for "every bundle ever signed by any v1.0.x release" — which must now name the v1.1.x and v1.2.x lines too.

## Hard constraints

1. **Bundle compatibility is forever** (Principle 1). `fixtures/v101/` and `fixtures/v110/` are NEVER regenerated. Phase 0 freezes a **third** fixture (v1.2.2-era, no attestation) *before* any engine change, so the exact format this release supersedes has a frozen witness.
2. **`verify`'s legacy seven-key JSON is byte-identical forever** — `verified, evaluation_status, errors, warnings, artifacts_checked, artifacts_missing, artifacts_tampered`, in that order, with their frozen values (`:1418-1435`). Never insert among the first seven; never change `verified = len(errors) == 0`; never change the exit codes at `:1440`. New keys append after `bundle`.
3. **An absent attestation is silent.** `check("attestation", "skipped", …)` and **zero errors, zero warnings, in every mode including `--strict`**. No version→attestation implication (finding 12).
4. **`cmd_verify` never touches the filesystem for attestation purposes** (finding 6). `resolve_verify_anchor` stays unchanged; the `.rpack` remains a receipt that verifies alone from any cwd.
5. **Stdlib only.** Pure-stdlib JSON plus a pure-Python Ed25519 primitive (`hashlib` + int arithmetic; no `cryptography`, no `secrets`-driven nondeterminism — Ed25519 signing is deterministic, which is what makes the sidecar reproducible). **cosign is consumer-side only** (Principle 2).
6. **`cmd_preflight` is NOT modified.** Its overall `ok` is `all(c["ok"] …)` (`:348`), so a cosign check would fail Phase 0 for every user without it, and README:29-35 tells users preflight checks "all of this". A grep test asserts `cosign` never appears in preflight's checks.
7. **Single-file engine.** The Action vendors `forgeproof.py` and CI sync-checks its SHA-256 (`PLAN_v1.2.0.md:15`). No new modules. The ~500 new lines and their comments must not contain any literal banned by `test_engine_source_has_no_shell_isms` (`shell=True`, `sha256sum`, `head -20`, `2>/dev/null`, `"which `, `shell_run`).
8. **Cross-platform.** `python3`-only Debian and Windows PowerShell 5.1. No `shell=True`; list-form subprocess with stdin closed and an explicit `timeout=`.
9. **Attestation content is attacker-controlled in the audit report.** Every predicate-derived string in the Markdown report goes through `md_cell()` (`:1034-1044`) — approver emails and notes land in PR comments.
10. **`hooks/hooks.json` does not change.** `cmd_gate_pr` and `cmd_lint_hook` stay attestation-unaware: the gate keeps its 10 s budget and its `*.rpack` glob; lint-hook's `chain-*.json` glob must never widen to `*.json` (a committed `issue-N.sigstore.json` would then look like an active run).
11. **Validate invocation**: always `claude plugin validate .claude-plugin/plugin.json`, never `.` (marketplace mode).

## Summary

v1.3.0 makes every run emit a standards-conformant attestation alongside its `.rpack`: an **in-toto Statement v1** (`https://in-toto.io/Statement/v1`) carrying a **SLSA Provenance v1** predicate (`https://slsa.dev/provenance/v1`), in a **DSSE envelope** (`application/vnd.in-toto+json`) inside a **Sigstore bundle** (`application/vnd.dev.sigstore.bundle.v0.3+json`), signed with the *same* ephemeral Ed25519 key that signs the chain — via a new pure-Python RFC 8032 signer whose seed is parsed out of the OpenSSH private key the engine already writes. The bundle is embedded in the `.rpack` (so `root_digest` covers it and old verifiers still pass) and exported byte-identically to `.forgeproof/issue-N.sigstore.json`, with the key as `.forgeproof/issue-N.pub.pem`; both are swept up by the existing seal commit. The predicate carries builder identity with **per-field provenance labels** — model `self-reported`, Claude Code version `measured`, plugin version — plus **human approval events** captured through a new `approval` chain action. `verify` gains three additive attestation checks that are tamper-class when an attestation is present and `skipped` when absent, and never reads a file to decide. A required `cosign-interop` job with a pinned cosign binary proves the ROADMAP criterion mechanically. Two new docs map the output to the SSDF/CISA-form and EU CRA landscape as it actually stands in 2026, and state the honest limit: SLSA Build **L1** by construction.

### Phase 1 — Engine: cryptographic primitives (`skills/run/scripts/forgeproof.py`)

Pure functions in a new `# --- Raw Ed25519 (RFC 8032) — the cosign-verifiable tier ---` section after the existing Signing section (`:128-227`). Nothing is wired into the lifecycle, so this phase cannot change existing behavior. **Do not touch `sign_ed25519`, `verify_signature`, or `signature_is_canonical`** — SSHSIG stays exactly as ssh-keygen produces it; if the DSSE signature field needs a canonicality guard, write a separate strict-base64 validator beside it.

1. **RFC 8032 Ed25519**: `ed25519_public_from_seed`, `ed25519_sign(seed, msg)`, `ed25519_verify(pub, msg, sig)`. Curve constants module-level, defined before first use. **Hardening is part of the acceptance criteria, not an extra**: reject non-canonical `s >= L` (signature malleability — the exact class this repo has already patched twice), validate point decompression (reject `y >= q` and non-square `x`), and reject encrypted or non-ed25519 keys outright.
2. **`openssh_ed25519_seed(private_path) -> bytes`**: parse the unencrypted `openssh-key-v1` container (magic; `none` cipher/kdf; one key; length-prefixed fields; private section = check-int ×2, `ssh-ed25519`, pub(32), priv(64 = seed‖pub), comment, padding). **Asserts the derived public key equals the key blob**; any structural surprise `die()`s with an actionable message, never a traceback. `generate_ephemeral_keypair`'s `-N ""` becomes a documented load-bearing contract (add the comment).
3. **`ssh_ed25519_pubkey_bytes(pub_line) -> bytes`**: split on whitespace, require `fields[0] == "ssh-ed25519"`, base64-decode `fields[1]`, validate the SSH blob header, ignore the rest (the comment may itself contain spaces — see finding 15).
4. **`ed25519_spki_pem(pub) -> str`**: `ED25519_SPKI_PREFIX = bytes.fromhex("302a300506032b6570032100")` (12 bytes, RFC 8410 §10.1) + the 32 raw bytes = exactly 44 bytes DER. Emit exactly `-----BEGIN PUBLIC KEY-----` / `-----END PUBLIC KEY-----` (sigstore accepts only `PUBLIC KEY` and `RSA PUBLIC KEY` block types), LF line endings. Free self-check: every such body starts with `MCowBQYDK2VwAyEA`.
5. **`dsse_pae(payload_type, payload) -> bytes`** = `b"DSSEv1 " + len(type) + b" " + type + b" " + len(body) + b" " + body`, ASCII decimal lengths, no leading zeros, exactly four SP bytes, no trailing separator.
6. **Envelope + bundle builders.** Standard base64 **with padding** for `payload` and `sig` (protojson round-trips that byte-identically, which the sidecar contract needs). Exactly **one** signature (`sigstore-go` errors `ErrDSSEInvalidSignatureCount` otherwise). `keyid == verificationMaterial.publicKey.hint == base64_std(sha256(spki_der))` — the proto *requires* the two hints be identical. `dsseEnvelope` is a **sibling** of `verificationMaterial`, not nested. **protojson rejects unknown fields: no ForgeProof-specific keys anywhere in the bundle wrapper** — everything ForgeProof-specific lives inside the in-toto predicate.
7. **The v1.4 seam:** a `signer` object exposing `.keyid`, `.public_bytes`, `.sign(bytes)`, `.verification_material() -> dict`. v1.3 ships `EphemeralEd25519Signer`; v1.4's keyless tier implements the same four members and returns a Fulcio cert + Rekor `tlogEntries` from the last one, leaving the envelope byte-identical. Document it as the extension point.
8. **Unit tests** (`TestEd25519Primitive`, `TestOpenSSHKeyParse`, `TestDSSEEncoding`): RFC 8032 **§7.1 TEST 1/2/3** known-answer vectors (the RFC's "SECRET KEY" *is* the 32-byte seed, so it drops straight in); a malleability test (`s + L` must be rejected); a non-canonical point-encoding rejection; round-trip against a real `ssh-keygen` key (CI-escalating skip); corrupt/truncated/encrypted key → clean `die()` via `_no_traceback`; PAE known-answer; PEM golden string; a timing floor (signing ≪ 1 s).

Verification: full pytest green; no new imports beyond `base64`/`struct`; the banned-literal grep test still passes.

### Phase 2 — Engine: attestation emission

1. **`approval` chain action.** `RECORD_FLAG_SPEC` (`:635-641`) gains `"approval": {"required": ["gate", "decision"], "optional": ["note"]}`; `_RECORD_DATA_FLAGS` (`:643-648`) gains `gate, decision, note` (finding 10 — without this the values are silently dropped). Add an `if action == "approval":` branch **before** the trailing lint-result return, and make that fallthrough explicit (`if action == "lint-result"` + a final `die`) so a future unbranched action fails loudly. `build_parser` (`:1849-1878`) gains `--gate`, `--note`, and `--decision` **with `choices=["approved", "rejected", "changes-requested"]`** (bounded values suit a compliance field and keep `_flag_name` error text unambiguous next to the existing `decision` *action*). Append the approval mapping to `_RemovedDataFlag`'s migration message. Note `--action` choices come from `sorted(RECORD_FLAG_SPEC)`, so `approval` sorts first in `--help`.
2. **Approver lookup** goes through a **single patchable module-level helper** using list-form `run(["git", "config", "user.email"], timeout=…)`, degrading to `""` on non-zero exit, empty output, missing git, or timeout — **never dies, never blocks a record**. This matters because `TestSkillContract` executes `_record_data_from_flags` for real on every documented invocation, and the `python3`-only Debian CI container has git with no identity configured. Every approval-shape test patches the helper.
3. **Builder identity into the finalize block.** `finalize_data` (`:829-834`) gains `builder` = model (`self-reported`), Claude Code version (`measured`), plugin (`PLUGIN_VERSION`). Read the flag as `model = getattr(args, "model", None); model = model if isinstance(model, str) else ""` — the same discipline as `cmd_verify:1152-1158`, because a MagicMock namespace returns a truthy Mock that would reach `json.dumps` and raise. Probe the CLI version through `shutil.which` **only** (never exec `CLAUDE_CODE_EXECPATH` directly; note `.cmd` on Windows), with an explicit `timeout=` and `TimeoutExpired` caught → `"unknown"`; `TestFinalizeRecheck._finalize` already patches `fp.shutil.which -> None`, so routing both lookups through it keeps that test meaningful. **Do not put `--model` on `init`** — genesis's key set is snapshot-tested against v1.0.1 literals and the frozen fixtures. New module constant `PLUGIN_VERSION` plus a test asserting it equals `.claude-plugin/plugin.json`.
4. **Statement builder** — `build_intoto_statement(...)`, deterministic and time-free (all timestamps come from chain blocks):
   - **`subject`** = one entry per deduped bundle artifact (`name` = repo-relative path, `digest.sha256`), derived from the artifact list built at `:855-880`, never a second walk of the chain. `subject` **may not be empty** (the in-toto reference validator raises `ErrSubjectRequired`; sigstore-go raises "no subjects found in statement"), so a zero-file-edit run emits exactly one entry: `{"name": ".forgeproof/chain-N.json", "digest": {"sha256": <chain_hash>}}`. Always include a `sha256` key — cosign's claim verifier hard-codes `subj.Digest["sha256"]` and **never reads `name`**.
   - `buildDefinition.buildType` = a ForgeProof URI documenting this schema; `externalParameters` = issue, requirements, **approvals** (each labelled `evidence: agent-recorded`); `internalParameters` = builder identity with its per-field `source` labels; `resolvedDependencies` = the `branch-create` block as `git+<repo>@refs/heads/<base>` with `digest.gitCommit`.
   - `runDetails.builder.id` = plugin repo + version (SLSA calls this "the sole determiner of the SLSA Build level"); `metadata.invocationId` = the genesis block hash (deterministic); `startedOn`/`finishedOn` = genesis/finalize timestamps, RFC 3339 UTC; `byproducts` = the chain descriptor and the evaluation summary (a ResourceDescriptor may carry base64 `content`).
   - **The chain byproduct MUST reuse the `chain_hash` local** assigned at `:966` — literally the same variable. ### Phase 3 — Engine: verification of the attestation

Read-side only, additive, and **zero filesystem reads for attestation purposes** (constraint 4).

1. **Three new `checks` entries**, inserted after the coverage check (`:1388`), each `skipped` with no error and no warning when `"attestation" not in bundle`:
   - `attestation` — statement/envelope well-formed: `_type`, `predicateType`, `payloadType`, decodable payload, exactly one signature.
   - `attestation_signature` — DSSE signature verifies over `PAE(payloadType, payload)`, **and the raw 32-byte DSSE key equals the key parsed from the bundle's own `ssh-ed25519 public_key` field**. Verifying against a key carried inside the attestation itself would prove nothing; this binding is the payoff of the one-key decision.
   - `attestation_subjects` — the subject set equals the bundle's artifacts exactly (or the single chain descriptor for a zero-artifact bundle), and the chain byproduct digest equals `bundle["chain_hash"]` (never recomputed — finding 8).
2. **Invariants, not byte re-derivation.** Verify must never rebuild the statement and compare bytes: a future predicate change would then turn valid *old* bundles red. These invariants stay forward-compatible with predicate evolution.
3. **Failure classification.** Signature / key-mismatch / subject / chain-digest failures are tamper-class and get **explicit new entries in `TAMPER_ERROR_MARKERS`**; their strings must avoid the fragments `hash mismatch` and `prev_hash` (finding 11), and a test must assert every new error string matches exactly one marker. A *malformed* attestation on a bundle whose root digest is intact is a plain error (VERIFICATION FAILED, not TAMPER) — that means it was signed malformed, an engine bug, not alteration. **No new error or warning may carry `STRICT_PREFIX`.**
4. **Version check — three call sites change together** (`:1175` equality, `:1179` warning, `:1183-1186` check status/detail). Membership in `KNOWN_RPACK_VERSIONS` replaces equality, and the detail string must print the **bundle's** version, not `RPACK_VERSION` — otherwise a frozen v1.0.0 fixture gets labelled "forgeproof-rpack v1.1.0" in an audit report. Changing only some of the three re-introduces a spurious warning on every legacy bundle, forever.
5. **Additive output.** A new top-level `attestation` object in the result: `{present, predicate_type, subject_count, key_id, builder, approvals}`. `bundle_summary` (`:1406-1416`) and the `checks` list are asserted by **hard equality** in `TestVerifyContract.test_new_keys_shape` (`:2619-2650`) — updating those two assertions is a required, deliberate task, not incidental.
6. **Markdown report** — a new `### Attestation` section modelled on Decisions/Evaluation: predicate type, builder id, model rendered with its `self-reported` label, subject count, approvals (sourced from `bundle["attestation"]`), and the exact `cosign verify-blob-attestation` command to reproduce the check. **Everything through `md_cell()`** (constraint 9). The checks table picks up the new rows automatically.
7. **Unit tests** (`TestVerifyAttestation`): a tamper matrix breaking each invariant individually (payload byte flip, signature byte flip, subject digest edit, DSSE key swapped for a different key, chain byproduct edit); a no-attestation bundle reports `skipped`, `warnings == []`, `errors == []`, in lenient **and** strict; malformed reads FAILED not TAMPER; the seven-key snapshots re-asserted. Add to **all three** frozen-fixture classes: `statuses["attestation"] == "skipped"`, `output["warnings"] == []`, and `check("format")` is `ok` with the **bundle's** version in its detail — lenient and strict (finding: those classes assert `errors == []` but have never asserted `warnings == []`).

Verification: full pytest green; three frozen fixtures green on every CI platform; a deliberately tampered v1.3 bundle red with an accurate verdict line.
